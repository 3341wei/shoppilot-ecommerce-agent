## 1. P0：买家闭环 Demo（约 9–11 人日）

**目标**：买家能完成「找货 → 查订单 → 判售后 → 建工单」全流程，工程骨架完整、测试可跑。

| # | 任务 | 产出 | 估算 |
|---|---|---|---|
| 1 | 工程骨架 | 复制并裁剪参考项目的 `core/`、`main.py`、SSE、健康检查；新增 SQLite 配置 | 0.5 |
| 2 | 数据模型与 seed | `schema.sql` + `scripts/seed_db.py` + 24 商品/12 订单/7 政策 | 1.0 |
| 3 | 业务服务层 | `catalog / orders / logistics / promotions / after_sales` | 1.5 |
| 4 | 规则引擎 | `rules.py`：到手价、退换资格、库存预警 + 单测 | 1.0 |
| 5 | 检索链路 | 双 collection、结构化过滤、混合检索、rerank 降级、ingest | 1.0 |
| 6 | P0 工具层 | 约 12 个工具 + 角色注册表 + artifact | 1.0 |
| 7 | Agent 服务 | 双角色 Agent、提示词、SSE 事件、工具调用上限 | 1.0 |
| 8 | 确认单机制 | `actions.py`：签发/校验/TTL/幂等/审计 + 接口 | 0.75 |
| 9 | 前端 | 聊天、商品卡、订单卡、物流时间轴、确认卡、来源 | 1.5 |
| 10 | 测试与调优 | 规则/确认单/工具/接口测试；提示词与工具描述调优 | 1.0 |
| | **合计** | | **10.25** |

**P0 工具范围（12 个）**
`search_products`、`get_product_detail`、`check_stock`、`calc_best_price`、
`get_order`、`track_logistics`、`search_after_sales_policy`、`check_return_eligibility`、
`create_after_sales_ticket`、`handoff_to_human`、`calculator`、`get_current_time`。

**P0 出口标准**

- 四个验收剧本 + 一个越权剧本全部跑通（见 §4）
- 买家工具集中不含任何运营工具
- 写操作未确认不落库，重复确认幂等
- `pytest` 全绿、`ruff check` 通过、本地 30 秒内跑完
- 无 Key 时相关接口返回 503，但前端与健康检查可用

**裁剪方案（如果只想先看效果，约 5–6 人日）**
只做「售前导购 + 售后政策」：商品检索/详情/库存/价格 + 政策 RAG + 资格判定（只读，不含工单）。
好处是最快看到 Agent 效果；代价是缺少写操作与确认机制这个最大亮点。

## 3. P2：进阶与生产化（按需，约 8–12 人日）

| 方向 | 内容 | 价值 |
|---|---|---|
| 身份与安全 | JWT/OAuth 替换演示头，订单归属从令牌解析 | 生产可用 |
| 扩展性 | Redis checkpointer + 多 worker；SQLite → PostgreSQL | 水平扩展 |
| 可观测 | Prometheus 指标、LLM 调用链追踪、成本看板 | 可运营 |
| 高级 HITL | LangGraph interrupt 实现多步审批（改地址 → 主管审） | 更复杂写操作 |
| 渠道接入 | 企业微信/公众号 webhook、消息适配层 | 真实触点 |
| 平台适配 | 淘宝/京东/Shopify adapter 接口 + 签名/重试 | 真实数据 |
| 多租户 | tenant_id 隔离数据与索引 | SaaS 化 |
| 子 Agent | 按域拆分 + 路由，解决工具过多 | 可维护性 |

> P2 不建议一次全做。优先做「身份 + 部署 + 可观测」，这三块最能在面试里讲清楚工程判断。

## 4. 验收剧本（P0 逐条演示）

### S1 售前导购（买家）

```text
用户：预算 500 以内，给刚开始跑步的人推荐双跑鞋，有满减吗？

期望：
1. 调用 search_products(category=运动鞋, max_price=500)
2. 对 2–3 款调用 get_product_detail / check_stock
3. 调用 calc_best_price
4. 输出商品卡 + 到手价明细 + 商品来源
5. 不推荐断货款；理由来自商品属性
```

### S2 订单物流（买家）

```text
用户：订单 SO20261001003 到哪了？手机尾号 8821。

期望：
1. get_order 校验归属与尾号
2. track_logistics 返回时间轴
3. 若停滞 > 48h，主动提示异常与建议
4. 卡片中的手机号、地址为脱敏值

反例：用买家 B 查询买家 A 的订单 → 403 ORDER_FORBIDDEN，不泄露任何订单字段
```

### S3 售后工单（买家，写操作）

```text
用户：两周前买的降噪耳机，拆封了但不喜欢，能退吗？

期望：
1. search_after_sales_policy + check_return_eligibility
2. 结论：超过 7 天且已拆封，不支持无理由；可保修
3. 给出替代方案；用户要求报修
4. create_after_sales_ticket 返回待确认卡片，数据库此时无工单
5. 点击确认 → 生成 AS 开头工单号；再次确认返回同一工单
6. 数据库与审计日志各一条记录
```

### S4 运营分析（运营）

```text
运营：上周退款率为什么涨了？哪个类目拖后腿？库存呢？

期望：
1. get_sales_overview(上周) → 退款率环比
2. 下钻类目 → 定位最高类目
3. analyze_reviews 给出差评主题与代表评论
4. get_inventory_alerts 给出补货建议
5. 结论区分数据事实与推测，附指标口径
```

### S5 角色隔离

```text
买家：帮我看下上周 GMV。
期望：不调用运营工具，回答“该功能仅运营角色可用”，或引导至对应入口。
（服务端同时保证：即使伪造工具名，工具注册表也不存在该工具）
```

## 5. 风险与对策

| 风险 | 影响 | 概率 | 对策 |
|---|---|---|---|
| LLM 工具选择不稳定 | 答非所问、漏调工具 | 中 | 工具描述写清“何时必须调用”；评测集回归；关键路径加确定性兜底 |
| 工具过多导致准确率下降 | 选错工具 | 中 | P0 控制在 12 个；按角色裁剪；P2 再拆子 Agent |
| 写操作被误触发 | 资损/投诉 | 低 | 确认单 + 服务端校验 + 幂等 + 审计；不做自动退款 |
| 演示角色头被伪造 | 越权 | 演示可接受 | README 与代码注释明确“仅演示”；生产用 JWT（P2） |
| 商品语义检索效果差 | 推荐不准 | 中 | 结构化过滤前置 + 混合检索 + rerank；空结果兜底 |
| SQLite 并发写锁 | 偶发 500 | 低 | WAL + 短事务 + 重试；写操作串行化 |
| LLM 成本/延迟 | 演示卡顿 | 中 | 限制工具次数与上下文长度；流式输出；开发期可用缓存 |
| 政策文档更新后回答过时 | 合规风险 | 低 | 回答带来源与生效日期；重建索引流程；P2 增量更新 |
| 范围膨胀 | 做不完 | 高 | 严格按 P0 清单；运营能力全部放 P1；“不做清单”写死 |

## 6. 建议的开工顺序

```text
Week 1：工程骨架 → seed 数据 → 规则引擎（先把“算得对”做扎实）
Week 2：检索 → 工具层 → 买家 Agent 流式闭环
Week 3：确认单 → 前端卡片 → 测试与剧本联调
Week 4（可选）：运营工具 + 看板 + 评测 + Docker/CI
```

**第一个可演示节点**：Week 2 结束，能完成 S1（导购）与 S2（订单物流）。
**第二个可演示节点**：Week 3 结束，S3/S5 通过，即完整 P0。

## 7. 开工前确认项

1. 是否认可「双端定位，P0 先做买家闭环」？
2. 是否接受「内置 mock 数据、不接真实平台」？
3. 写操作是否只做到「工单创建 + 确认制」，不做自动退款/改地址？
4. 前端 P0 是否只做聊天 + 富卡片，运营看板放 P1？
5. 是否需要我先补一份「接口字段级设计」或「数据库 DDL」再开工？

确认后我从 P0 第 1–2 步开始：工程骨架 + seed 数据，先让项目能跑起来，再逐步接 Agent。
